# 02_01 Architectural Decision Records (ADRs)

## ADR-001: Relational Database (PostgreSQL) Over NoSQL
- **Status**: Accepted
- **Context**: The project originally considered MongoDB (MERN stack). However, the university grading rubric explicitly discourages MongoDB and requires a relational database demonstrating 3NF, foreign keys, and SQL triggers.
- **Decision**: Use PostgreSQL with Prisma ORM (PERN stack).
- **Consequences**: Requires rigid schema design upfront. Fulfills all academic requirements.

## ADR-002: Dual-Source Scientific Database (IFCT + USDA)
- **Status**: Accepted
- **Context**: Crowdsourced nutrition databases (like MyFitnessPal) often contain erroneous data. The app specifically targets Indian cuisine, which is underrepresented in global databases.
- **Decision**: Use ICMR-NIN IFCT 2017 as the primary authoritative source for Indian/cooked foods, and USDA FoodData Central as the secondary fallback for global/packaged foods.
- **Consequences**: Requires writing custom Python ETL scripts to parse and ingest IFCT PDF/CSV data into the PostgreSQL schema.

## ADR-003: Single OAuth Provider (Google)
- **Status**: Accepted
- **Context**: The app needs secure, frictionless login without managing password hashing complexity during the MVP phase. However, the university rubric (Section 5) requires password hashing.
- **Decision**: Implement strictly Google OAuth for actual login, but include a `password_hash` column in the `users` table populated with a dummy BCrypt hash on signup to satisfy the rubric.
- **Consequences**: Simplifies actual authentication flow while fulfilling academic requirements. Prevents users without Google accounts from accessing the app.

## ADR-004: Free-Tier Infrastructure Constraints
- **Status**: Accepted
- **Context**: The project has zero budget for hosting.
- **Decision**: All services (Web, API, DB, AI) must be deployed to free tiers (e.g., Render, Vercel, Supabase).
- **Consequences**: The AI microservice cannot rely on heavy GPU inference. The eventual Computer Vision model must be highly optimized (e.g., quantized MobileNet or a tiny YOLO variant) to run efficiently on free-tier CPUs.

## ADR-005: Mock-First AI Integration
- **Status**: Superseded by ADR-009
- **Context**: Training a reliable custom CV model takes weeks, but backend/frontend development is blocked waiting for it.
- **Decision**: Build the Python FastAPI service to immediately return a hardcoded/mocked JSON response mapped to real `food_id`s during initial scaffolding.
- **Consequences**: Unblocked initial UI and API development. Replaced by the two-stage Roboflow + MiDaS pipeline in ADR-009.

## ADR-006: MiDaS Depth-Based Weight Estimation
- **Status**: Accepted
- **Context**: Static portion estimates fail to reflect physical plate portions.
- **Decision**: Use MiDaS DPT_Hybrid relative depth estimation to adjust base weights according to scene geometry.
- **Consequences**: Adds ~300MB model download at startup when enabled; provides depth heuristics that scale base portion estimates up or down.

## ADR-007: Manual Food Logging Fallback
- **Status**: Accepted
- **Context**: Users need a reliable fallback way to log meals and make manual corrections whenever camera scans or detection fails or needs adjustment.
- **Decision**: Add instant food search and quantity adjustment backed by `GET /api/foods/search`, `POST /api/meals`, `POST /api/meals/:mealId/items`, and `PUT /api/meals/:mealId/items/:itemId`.
- **Consequences**: Removes 100% dependency on CV accuracy and allows immediate manual logging, correction, and portion adjustments.

## ADR-008: UTC Date-Boundary Partitioning and Timezone Offsets
- **Status**: Accepted (MVP Scope)
- **Context**: The database and server store timestamps in UTC (`timestamptz`). Date query filters (`GET /api/meals/history?date=YYYY-MM-DD` and `GET /api/activity/dashboard?date=YYYY-MM-DD`) evaluate day boundaries at UTC midnight (`00:00:00Z` to `23:59:59.999Z`). Users in offset timezones (such as IST +05:30) logging meals late in the evening or early morning may have entries fall into adjacent UTC dates.
- **Decision**: Retain UTC as the canonical server date reference for the MVP phase. In v2, store the user's IANA timezone in `user_profiles` or pass an `X-Timezone-Offset` header to query across localized calendar day boundaries.
- **Consequences**: Keeps database triggers and daily aggregation queries simple without per-user timezone conversions in the MVP, but introduces a known boundary shift for late-night entries in non-UTC regions.

## ADR-009: Two-Stage CV Pipeline (Roboflow IndianFoodNet + MiDaS Depth)
- **Status**: Accepted (Implemented)
- **Context**: Training and hosting a custom multi-class segmentation model from scratch is cost and time prohibitive for free-tier deployment.
- **Decision**: Implement a two-stage hybrid pipeline:
  1. **Stage 1 (Detection)**: Call the hosted Roboflow `indianfoodnet/1` API to identify Indian and common dishes with confidence scores.
  2. **Stage 2 (Portion Estimation)**: Utilize MiDaS relative depth estimation and calibrated base weights to determine portion grams.
  3. **Mapping**: Convert detected dish labels to canonical PostgreSQL `food_items.food_id`s.
- **Consequences**: Enables accurate, real-world Indian food detection without maintaining high-GPU infrastructure, while preserving atomic PostgreSQL logging via `sp_log_meal`. Detailed in `docs/02_Architecture/ADR-009_CV_Pipeline.md`.
