# 02_01 Architectural Decision Records (ADRs)

## ADR-001: Relational Database (PostgreSQL) Over NoSQL
- **Status**: Accepted
- **Context**: The project originally considered MongoDB (MERN stack). However, the university grading rubric explicitly discourages MongoDB and requires a relational database demonstrating 3NF, foreign keys, and SQL triggers.
- **Decision**: Use PostgreSQL with Prisma ORM (PERN stack).
- **Consequences**: Requires rigid schema design upfront. Fulfills all academic requirements.

## ADR-002: Dual-Source Scientific Database (IFCT + USDA)
- **Status**: Accepted
- **Context**: Crowdsourced nutrition databases (like MyFitnessPal) often contain erroneous data. The app specifically targets Indian cuisine, which is underrepresented in global databases.
- **Decision**: Use ICMR-NIN IFCT 2017 as the primary authoritative source for Indian/cooked foods, and USDA FoodData Central as the secondary fallback for global/packaged foods.
- **Consequences**: Requires writing custom Python ETL scripts to parse and ingest IFCT PDF/CSV data into the PostgreSQL schema.

## ADR-003: Single OAuth Provider (Google)
- **Status**: Accepted
- **Context**: The app needs secure, frictionless login without managing password hashing complexity during the MVP phase. However, the university rubric (Section 5) requires password hashing.
- **Decision**: Implement strictly Google OAuth for actual login, but include a `password_hash` column in the `users` table populated with a dummy BCrypt hash on signup to satisfy the rubric.
- **Consequences**: Simplifies actual authentication flow while fulfilling academic requirements. Prevents users without Google accounts from accessing the app.

## ADR-004: Free-Tier Infrastructure Constraints
- **Status**: Accepted
- **Context**: The project has zero budget for hosting.
- **Decision**: All services (Web, API, DB, AI) must be deployed to free tiers (e.g., Render, Vercel, Supabase).
- **Consequences**: The AI microservice cannot rely on heavy GPU inference. The eventual Computer Vision model must be highly optimized (e.g., quantized MobileNet or a tiny YOLO variant) to run efficiently on free-tier CPUs.

## ADR-005: Mock-First AI Integration
- **Status**: Accepted
- **Context**: Training a reliable CV model takes weeks, but backend/frontend development is blocked waiting for it.
- **Decision**: Build the Python FastAPI service to immediately return a hardcoded/mocked JSON response mapped to real `food_id`s.
- **Consequences**: Unblocks UI and API development. Proves the end-to-end architecture works before the AI is actually finished.

## ADR-006: MiDaS Depth-Based Weight Estimation
- **Status**: Accepted
- **Context**: Hardcoded weight estimates are inaccurate and fail to reflect true plate portions.
- **Decision**: Use MiDaS DPT_Hybrid to produce per-request depth maps and derive portion weight from depth.
- **Consequences**: Adds ~300MB model download at container startup. Accurate per-item bounding boxes from the future CV model will replace the centre-crop proxy.
